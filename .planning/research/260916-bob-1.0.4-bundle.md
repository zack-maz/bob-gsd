# Bob Shell 1.0.4 — reverse-read of the shipped bundle

**Subject:** `bobshell@1.0.4`, `/opt/homebrew/lib/node_modules/bobshell`, bundle
`bundle/bob.js` (12,758,206 bytes, minified). `package.json`: `"version": "1.0.4"`,
`"engines": {"node": ">=20.0.0"}`, `"type": "module"`, `bin.bob = bundle/bob.js`, one runtime
dep (`pdf-parse`) plus optional `node-pty` variants.
**Method:** string/RegExp extraction over the bundle via node scripts (`scratchpad/x.mjs`,
`scratchpad/c.mjs`); every claim below is backed by a decoded snippet. Bundled documentation at
`bundle/bobshell-docs/` (14 `.md` files) was read too and is cited **only** where it agrees or
conflicts with the code — **the code is the authority**.
**Comparison baseline:** `.planning/phases/12-bob-2-0-capability-re-verification/12-BOB2-EVIDENCE.md`
(Bob Shell 2.0.1).

**Provenance:** the bundle is a fork of **Gemini CLI**. The path class is literally still named
`getGlobalGeminiDir`/`getGeminiDir`, with the directory constant rebound to `.bob`. This explains
most of 1.0.4's surface: it is Gemini CLI's config/command/hook/subagent machinery with IBM
overrides and a Roo/Cline-style modes+rules layer grafted on.

- The global scope accepts **both** `.yaml` and `.json`; the project scope reads **only**
  `custom_modes.yaml`, but sniffs its content (`startsWith("{")` → JSON.parse, else YAML).

- The project migration source is **`.bobmodes`** (a file in the workspace root), **not**
  `.bob/modes` as hinted. No `.bob/modes` path exists in the bundle.
- **The bundled 1.0.4 doc is wrong.** `bobshell-docs/custom-modes-bobshell.md` says "Create or
  edit `~/.bob/custom_modes.yaml` for modes available across all projects" and lists precedence
  as "User-level modes (`~/.bob/custom_modes.yaml`)". The code reads `~/.bob/settings/`. A file
  written to the home root is silently *moved* on next launch (and only if the `settings/` one is
  absent).

### 2.2 Schema accepted

There is **no zod schema** for modes in 1.0.4 — validation is a hand-written function:

```js
function wui(t){ return !t.slug||typeof t.slug!="string" ? "Mode must have a valid slug"
  : !t.name||typeof t.name!="string" ? `Mode ${t.slug} must have a valid name`
  : !t.roleDefinition||typeof t.roleDefinition!="string" ? `Mode ${t.slug} must have a valid roleDefinition`
  : Array.isArray(t.groups) ? null : `Mode ${t.slug} must have a valid groups array` }
```

Merge / defaulting:

```js
function bdr(t,e,r){                       // t=built-ins, e=global, r=project
  let n=new Map;

  for(let o of e){ o.groups=o.groups||[], o.groups.push("think");

    n.set(o.slug,{...o}) }
  for(let o of r){ o.groups=o.groups||[], o.groups.push("think");
    let s=wui(o); if(s){ console.warn(`Skipping invalid project mode: ${s}`); continue }
    n.set(o.slug,{...o}) }
  return n.forEach(o=>{ o.description=o.description||"<no description>" }), Array.from(n.values())
}
async function lut(t,e){ let[r,n]=await Promise.all([gva(e),Ava(e)]); … return bdr(t,r,n) }
```

- **Required:** `slug` (string), `name` (string), `roleDefinition` (string), `groups` (must be an
  Array — but may be empty; `groups: []` passes).
- **Optional / read:** `whenToUse` (surfaced in the `switch_mode` tool description and
  `--chat-mode` help), `customInstructions`, `description` (defaults to `"<no description>"`).
- Unknown keys are carried through untouched (`{...o}`) and ignored.
- **`"think"` is appended to every custom mode's `groups`** automatically. Built-ins are not
  touched.
- Precedence: built-ins < global < project (last write to the slug Map wins). A custom mode may
  therefore **override a built-in slug**.
- An invalid mode is skipped with a `console.warn` only.

### 2.3 Tool-group vocabulary — `groups` is open, and `command` is first-class

Group→tool matching happens in two twin loops (availability filter `Sle`, and the
not-available error message builder):

```js
let c=!1;
if(o?.groups) for(let f of o.groups){
  if(f==="*"){ c=!0; break }
  if(f==="mcp" && d && "serverName" in d && typeof d.serverName<"u"){ c=!0; break }
  if(typeof f=="string"){ if(ett(l,f)){c=!0;break} if(d&&f===d.kind){c=!0;break} }
  if(Array.isArray(f)&&f.length>=1){ let p=f[0];
    if(ett(l,p)){c=!0;break} if(d&&p===d.kind){c=!0;break} }
}
```

`ett` is a lookup into a fixed name→tool-set record:

```js
function ett(t,e){ let r=mGs[e]; return r ? r.has(t) : !1 }
mGs = {
  read:    new Set([read_file, list_files, search_file_content, glob, read_many_files,
                    generate_description_from_diff]),
  edit:    new Set([write_to_file, search_and_replace, save_memory, insert_content,
                    create_pull_request, apply_diff, replace_regex, restore]),
  browser: new Set([google_web_search, web_fetch]),
  command: new Set([execute_command])
}
```

(identifier→name constants resolved from the bundle: `Ac="read_file"`, `j6="list_files"`,
`cA="search_file_content"`, `HS="glob"`, `gk="read_many_files"`,
`Tve="generate_description_from_diff"`, `j_="write_to_file"`, `Q_="search_and_replace"`,
`mk="save_memory"`, `Cve="insert_content"`, `vve="create_pull_request"`, `_ve="apply_diff"`,
`wve="replace_regex"`, `xve="restore"`, `ez="google_web_search"`, `Eve="web_fetch"`,
`rg="execute_command"`.)

Tool `kind` values come from an enum:

```js
(function(t){ t.Read="read", t.Edit="edit", t.Delete="delete", t.Move="move", t.Search="search",
  t.Execute="execute", t.Think="think", t.Fetch="fetch", t.Other="other" })(en||(en={}));
mio=[en.Edit,en.Delete,en.Move,en.Execute];
```

**So a group token matches if it is any of:**

| Token | Matches via | Accepted in 1.0.4 |
|---|---|---|
| `*` | wildcard short-circuit | ✅ all tools |
| `read` | `mGs.read` **and** `kind==="read"` | ✅ |
| `edit` | `mGs.edit` **and** `kind==="edit"` | ✅ |
| `command` | `mGs.command` (→ `execute_command`) | ✅ **first-class group** |
| `execute` | `kind==="execute"` | ✅ |
| `browser` | `mGs.browser` (web search + fetch) | ✅ |
| `think` | `kind==="think"` (auto-appended to custom modes) | ✅ |
| `delete` `move` `search` `fetch` `other` | `kind` match | ✅ (kind-only) |
| `mcp` | special case: any tool with a `serverName` | ✅ |
| `skill` `todo` `subagent` `subtask` `mode` `artifact` `workflow` | nothing — no `mGs` entry, no tool `kind` | ❌ **inert** |

Two consequences worth stating precisely:

1. **`groups` is an open string list in 1.0.4 too.** An unrecognised token passes `wui`
   (`Array.isArray` is the only check), loads with no warning, and simply never matches a tool —
   the same silent-capability-loss failure mode recorded for 2.0.1 in BOB2-02.
2. **There is NO `command`→`execute` normalization in 1.0.4.** The 2.0.1 alias loop
   (`m === "command" ? "execute" : m`) does not exist here; instead `command` is a real key in
   `mGs`. Both `command` and `execute` therefore grant `execute_command` in 1.0.4, but by two
   different mechanisms. The polarity is inverted between versions:
   - 1.0.4: `command` = named group set; `execute` = tool-kind match.
   - 2.0.1: `command` = back-compat alias normalized to `execute`.

Always-available tools bypass the group check entirely:

```js
q4n = new Set([attempt_completion, switch_mode, update_todo_list, ask_followup_question,
               search_docs, write_todos]);
```

### 2.4 `fileRegex` tuples — accepted syntactically, **not enforced**

**`fileRegex` has 0 occurrences in the entire bundle.** The matcher does handle the tuple form
`[name, {...}]`, but only ever reads element `[0]`:

```js
if(Array.isArray(f)&&f.length>=1){ let p=f[0]; if(ett(l,p)){c=!0;break} if(d&&p===d.kind){c=!0;break} }
```

→ In 1.0.4 a mode declaring `- - edit` / `  - fileRegex: \.(sh|bash)$` gets **unrestricted
`edit`**. The tuple parses and the second element is discarded. The bundled doc
(`custom-modes-bobshell.md`) advertises `fileRegex` with a `description`; that is a Bob-IDE
feature the shell does not implement at this version. UNKNOWN whether 2.0.1 enforces it — the
Phase 12 evidence records only that the 2.0.1 schema *validates* the tuple
(`z.tuple([z.string(), Dws /* {fileRegex} */])`), not that it filters on it.

Resolution order for mode `<slug>`:

## 3. Slash commands

**Four loaders are registered** (`await Xfe.create([new ope(t), new Ffe(t), new ipe(t), new Fgt(t)], signal)`):

| Loader | What it loads |
|---|---|
| `ope` | MCP server prompts (`getMcpClientManager().getMcpServers()`) |
| `Ffe` | built-in commands (`/init`, `/memory`, `/settings`, …) |
| `ipe` | Gemini-CLI **TOML** file commands — glob `**/*.toml`, zod `{prompt: string (required), description?: string}` |
| `Fgt` | **IBM Markdown** commands — glob `**/*.md`, zod `{description?: string, "argument-hint"?: string}` |

Both file loaders scan the **same directories**:


- **Directories scanned:** `~/.bob/commands`, `<workspace>/.bob/commands`, plus
  `<extension>/commands` per active extension. **No `.gemini`, no `.agents`, no `.claude`**
  (`.agents` and `.claude` have 0 directory-literal occurrences; the only `.agents` hits in the
  bundle are `this.agents` property accesses).
- Glob options `{nodir:!0, dot:!0, follow:!0}` — recursive, dotfiles included, symlinks followed.
- **Folder trust gate:** `if(this.folderTrustEnabled && !this.isTrustedFolder) return []` — with
  folder trust on, an untrusted workspace loads **no** file commands at all (global ones included,
  since the guard is on the whole loader).

### 3.1 Markdown command format (`Fgt`, the IBM loader)

```js
var V9a = Xe.object({ description: Xe.string().optional(), "argument-hint": Xe.string().optional() });
…
let l = V9a.safeParse(a.data);
if(!l.success) return console.error(`[IBMMarkdownCommandLoader] Skipping invalid command file: ${e}. Validation errors:`, l.error.flatten()), null;
let d=l.data, c=a.content.trim();

    p=u.substring(0,u.length-3).split(ARe.sep)
       .map(D=>D.toLowerCase().replace(/\s+/g,"-").replace(/[^a-z0-9-]/g,"")
                 .replace(/-+/g,"-").replace(/^-|-$/g,"")).join(":"),

    y=d["argument-hint"]; y&&(y=`| arguments: ${d["argument-hint"]}`);
```

- **Frontmatter:** exactly `description` and `argument-hint`, both optional. Parsed by
  `gray-matter` (`zDi.default(s)`). The zod object is **not** `.strict()`, so extra keys
  (`allowed-tools`, `model`, `effort`, …) are **ignored, not fatal**. Confirms the adapter's
  MEDIUM assumption, and shows stripping is belt-and-braces rather than strictly required.
- **Empty body ⇒ command skipped** (after `.trim()`). A frontmatter-only file does not register.
- **Filename → command name:** path relative to the scanned dir, `.md` stripped, each path
  segment lowercased and slugified (`\s+`→`-`, non-`[a-z0-9-]` dropped, runs collapsed, edges
  trimmed), segments joined with **`:`**.
  → `gsd-plan-phase.md` ⇒ `/gsd-plan-phase`; `gsd/plan-phase.md` ⇒ `/gsd:plan-phase`.
- `argument-hint` is **not** a substitution mechanism — it is appended to the menu description as
  `| arguments: <hint>`.
- Extension-provided commands get their description prefixed `[<extensionName>]`, and name
  collisions are disambiguated as `<extensionName>.<name>`, `<extensionName>.<name>1`, … .

### 3.2 Argument substitution — `{{args}}`, **not** `$1`/`$2`/`$ARGUMENTS`

```js
var Zfe = class { async process(e,r){ return r.invocation?.args ? LXt(e, r.invocation.raw) : e } };
var LB = "{{args}}";
…
let _=[], S=c.includes(LB), T=c.includes("!{");
c.includes("@{") && _.push(new npe(p));      // @{path}  → file injection
(T||S)           && _.push(new tpe(p));      // !{cmd}   → shell injection, also does {{args}}
S                || _.push(new Zfe);         // no {{args}} → append raw args
```

with

```js
function LXt(t,e,r=`\n\n`){ if(!e) return t; … n[n.length-1]={...o, text:`${o.text}${r}${e}`}; … }
// and inside tpe: return [{ text: e.replaceAll(LB, n) }]   // n = invocation.args
```

Counts over the whole bundle: `"{{args}}"` → **1**, `"$ARGUMENTS"` → **0**.

- The **only** argument placeholder is **`{{args}}`**, replaced with the raw argument string.
- If the body contains **no** `{{args}}`, the raw arguments are **appended** to the prompt after a
  blank line (`Zfe`/`LXt`).
- **`$1` / `$2` positional substitution does not exist.** The bundled doc
  (`slash-commands-bobshell.md`) shows `Create a new API endpoint called $1 that handles $2
  requests.` — in 1.0.4 that text is passed to the model **verbatim** with the arguments glued on
  the end. The doc is wrong.
- Two further body-level features (shared with the TOML loader):
  - `@{path}` → injects file contents (`npe`; honours `.gitignore`/`.bobignore`).
  - `!{cmd}` → runs a shell command and injects its output, gated by a confirmation
    (`ConfirmationRequiredError` → `confirm_shell_commands`).
  - Unbalanced braces throw `Invalid syntax…: Unclosed injection…`.
- **Namespacing:** `:`-joined path segments (see above). Mode-switch commands are separate and, per
  the doc, cannot be overridden by file commands.

## Consequences for an installer that must support both

1. **The custom-mode paths are the good news: they are identical at both versions.**
   `modesRelPathForScope()` in `src/bob-adapter.cjs` — `settings/custom_modes.yaml` for global,
   bare `custom_modes.yaml` for local — is **correct for 1.0.4 as well as 2.0.1**. The
   asymmetry it encodes exists at both versions. No version branch is needed here. (The v0.2.2
   bug of writing `~/.bob/custom_modes.yaml` was wrong on 1.0.4 too — though 1.0.4 would have
   *renamed* the file into `settings/` on next launch, which 2.0.1 does not do, so the bug was
   self-healing on 1.0.x and permanent on 2.0.x.)

2. **The emitted group set `['read','edit','execute','mcp']` works unchanged on both.**
   On 1.0.4: `read` and `edit` match via both the named sets and tool `kind`; `execute` matches
   `kind==="execute"` (granting `execute_command`); `mcp` hits the `serverName` special case.
   The `gsd_run` / `gsd-tools.cjs` shell seam therefore resolves on 1.0.4. **Do not** widen the
   set to `skill`/`todo`/`subagent`/`mode`/`artifact`/`subtask` for 2.0.1's benefit without
   noting they are inert on 1.0.x — they are silently dropped, never an error.
   Adding `command` alongside `execute` would be harmless on both (first-class group on 1.0.4,
   alias on 2.0.1) but is redundant.

3. **`.bob/skills/gsd-*/SKILL.md` is completely inert on 1.0.4 — but harmless.** Nothing in the
   1.0.4 bundle enumerates `skills` or `SKILL.md`, so the tree is dead weight only. **The
   practical consequence is that `.bob/commands/` is the *only* GSD entry point on 1.0.x.** An
   installer that relies on skill auto-activation for any workflow will silently deliver nothing
   on 1.0.4. Every capability GSD needs must have a slash-command surface, and any
   skills-only workflow should be reported as unsupported when a 1.0.x host is detected.
   (Corollary: `src/installer/stage.cjs` should keep emitting both, and the
   parity/capability report should distinguish "emitted" from "reachable on this host".)

4. **`settings.json` is the one path that genuinely differs and must be branched** if the
   installer ever reads or writes it: `~/.bob/settings.json` on 1.0.4 vs
   `~/.bob/settings/settings.json` on 2.0.1. Writing the 2.0.1 path on a 1.0.4 host is a silent
   no-op, and vice-versa. Note the installer's existing care in `stage.cjs` about sweeping an
   installer-created `settings/` directory is still right — on 1.0.4 `settings/` may legitimately
   contain `custom_modes.yaml` and `mcp_settings.json` but **not** `settings.json`.

5. **MCP config differs in filename at global scope** — `~/.bob/settings/mcp_settings.json`
   (1.0.4) vs `~/.bob/settings/mcp.json` (2.0.1). Any Phase 15 MCP work must branch on version,
   or prefer the CLI (`bob mcp add …`), which exists on 1.0.4 and writes through the settings
   layer rather than a hardcoded path. The **project** path `<ws>/.bob/mcp.json` is the safer
   target on 1.0.4.

6. **Slash-command argument substitution is a real compatibility trap.** On 1.0.4 the only
   placeholder is `{{args}}`; `$1`/`$2`/`$ARGUMENTS` are passed to the model as literal text (and
   the raw arguments get appended to the prompt anyway). GSD command bodies must either use
   `{{args}}` or rely purely on the append behaviour. The 2.0.1 behaviour was never probed —
   **this is the highest-value remaining unknown** and should be checked in the 2.0.1 bundle
   before any command body is written to depend on a token. The bundled 1.0.4 doc's `$1`/`$2`
   example is wrong, so the docs cannot be used to settle it.

7. **Parallel execution planning must be version-gated.** `parallelSubagentFanout` is `true` on
   2.0.1 but on 1.0.4 there is **no subagent tool at all** — the machinery is compiled in with
   `enabled` pinned to `false` and no settings key to flip. Any GSD workflow needing subagents
   (isolated *or* parallel) is unsupported on 1.0.x, and the capability declaration should derive
   from the detected host version rather than a single static value. `gsd-autonomous`, which
   BOB2-05 marks supported on the strength of isolation, is **not** supported on 1.0.4.

8. **Commands are folder-trust gated on 1.0.4.** `if(this.folderTrustEnabled && !this.isTrustedFolder) return []`
   short-circuits the whole loader, and the IBM settings override forces
   `security.folderTrust.enabled ??= true`. On a fresh, untrusted workspace the installed GSD
   commands do not appear at all. Post-install guidance should mention `bob --trust` (or the trust
   prompt) — otherwise a correct install looks broken.

9. **Empty-body command files are dropped on 1.0.4** (`if(!c) … Skipping empty command file`).
   Any generated `.bob/commands/*.md` that is frontmatter-only will not register. Worth a
   converter assertion.

10. **Nested command directories change the command name.** Path separators become `:` after
    per-segment slugification, so `commands/gsd/plan-phase.md` is `/gsd:plan-phase`, not
    `/gsd-plan-phase`. Since gsd-core deprecated the colon form, the installer's flat
    `commands/gsd-<stem>.md` layout is the correct choice on 1.0.4 — keep it flat.

11. **Built-in mode slugs differ, and `--chat-mode` is strict.** `--chat-mode` is a yargs
    `choices:` list computed from the loaded mode slugs, so `bob --chat-mode=gsd` **fails
    argument parsing** (not a soft fallback) if the modes file was written to a path Bob does not
    read. That makes `--chat-mode=gsd` a cheap, non-inference acceptance probe for a correct
    modes install on either version. Also: 1.0.4's default mode is `code` and `advanced` exists;
    2.0.1 consolidated to `agent`/`plan`. Do not reference `code`/`advanced` or `agent` by name
    in emitted artifacts.

12. **`fileRegex` must not be relied on for safety on 1.0.4** — the tuple parses and the
    restriction is discarded, yielding unrestricted `edit`. If gsd-bob ever emits a scoped `edit`
    group, it is advisory on 1.0.x.

13. **Rules and AGENTS.md are usable on 1.0.4 and are a viable fallback surface.**
    `<ws>/.bob/rules-gsd/` (directory, recursive) or `.bobrules-gsd` (single file) inject
    mode-scoped instructions, and `~/.bob/AGENTS.md` / project `AGENTS.md` are read
    hierarchically with `@` imports. On a 1.0.x host where skills are dead, this is the only
    always-on instruction channel besides `customInstructions` in the mode itself. Note the
    mode-scoped fallback checks `.roorules-<slug>` **before** `.bobrules-<slug>`.

14. **Version detection is straightforward and should gate all of the above.** `bob --version`
    prints the hardcoded bundle version; the installed `package.json` at
    `<prefix>/lib/node_modules/bobshell/package.json` carries it too. Engine floors differ
    (`>=20` on 1.0.4 vs `>=22.15.0` on 2.0.x), so the adapter's `>=22.15.0` requirement remains
    the right floor for gsd-bob itself but must not be presented as a Bob requirement on 1.0.x.

### Marked UNKNOWN

- Whether Bob 2.0.1 supports `{{args}}` and/or `$1`/`$ARGUMENTS` in slash commands (not probed in
  Phase 12; highest-value gap).
- Whether 2.0.1 **enforces** `fileRegex` or merely validates it.
- 2.0.1's user/workspace `settings.json` workspace path, trusted-folders path, rules directories,
  AGENTS.md resolution, hook system, and `bob mcp` CLI — none recorded in the Phase 12 evidence.
- Whether the Bob **IDE** (as opposed to the Shell) reads the same `~/.bob` paths at either
  version; only the Shell side is observable from this bundle.
- Whether 1.0.4's `think` auto-append has a 2.0.1 analogue.
